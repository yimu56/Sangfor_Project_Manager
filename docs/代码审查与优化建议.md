# 代码审查与优化建议

> 审查对象：`Sangfor_Project_Manager`（v1.0.0，Go 1.26 + 纯 Go SQLite + 原生 JS）
> 审查日期：2026-11-06
> 审查方式：通读全部源码（Go 4.9k 行 / 前端 2.8k 行）+ `go vet` + `go build` + 起服务实测接口
> 说明：标注「实测」的条目都在临时数据目录里跑过真实请求；标注「代码推理」的条目未构造运行环境。

## 一、结论速览

整体是一个完成度相当高的个人工具：单二进制、零依赖、`embed` 内嵌前端、版本化附件、设备快照隔离、提醒去重，这些设计都做得克制且正确。SQL 全部参数绑定、写操作走字段白名单，基础安全做得比多数同类小工具好。

真正值得动手的是「一类模式化问题」而不是零散 bug：

| 维度 | 评价 | 说明 |
|---|---|---|
| 架构 / 数据模型 | **B+** | 25 表划分清晰，版本化 / 快照 / 继承三条主线一致 |
| 正确性 | **B-** | 3 个可复现的 bug（关联重复、到期当天状态、非法导出类型） |
| 安全 | **C** | 两个 XSS 注入面（附件 inline、内联 onclick 拼 JS）、API 404 回落 HTML、初始化无本机限制 |
| 性能 | **B-** | 大量 N+1 查询 + 列表二次全表查询，当前数据量下无感，量级一涨就线性劣化 |
| 可维护性 | **B** | 文件切分合理，但字段白名单 / 状态字典 / 渲染样板重复严重 |
| 工程化 | **C** | 0 测试、无 CI、gofmt 不干净、无 `.gitattributes`、无日志 |

**如果只做 5 件事**（按投入产出比排序）：

1. 附件按白名单决定 `inline` / `attachment`（S1）+ 干掉内联 `onclick` 里的字符串拼接（S2）—— 1 天，堵掉两个注入面。
2. `/api/*` 未命中直接 404 JSON，不再回落 `index.html` —— 10 分钟。
3. 修维保到期当天状态判断（Go 侧 1 行 + SQL 侧 2 处）—— 20 分钟。
4. 项目保存不再重复写 `project_relations`（加唯一索引 + 只在 create 时写）—— 1 小时。
5. 给 `hydrateProgress` 换成批量 `IN (...)` 查询 —— 2 小时，进度页 / 看板 / 导出三处同时受益。

## 二、安全

### S1（高危）上传的 HTML / SVG 附件可在站点同源执行脚本

**位置**：`internal/httpapi/handlers_customers.go:532-535`

```go
func serveInline(w http.ResponseWriter, r *http.Request, p string) {
	w.Header().Set("Content-Disposition", "inline")
	http.ServeFile(w, r, p)   // Content-Type 由扩展名推断
}
```

调用点：`handlers_projects.go:844`（`/api/files/{vid}`，附件与预览）、`handlers_customers.go:490`（`/api/blob/...`，拓扑图 / 验收单）。

**实测**：上传一个 `evil.html` 作为项目附件后：

```
GET /api/files/1
HTTP/1.1 200 OK
Content-Disposition: inline
Content-Type: text/html; charset=utf-8      ← 脚本会在本站源下执行
<script>fetch("/api/customers")...</script> ← 服务端原样返回
```

`X-Content-Type-Options: nosniff` 挡不住「声明为 `text/html` 的响应」。Cookie 虽然是 `HttpOnly`，但脚本可以直接带着同源 Cookie 调 `/api/*`，等于把全部数据（含客户设备明文密码）读走或删掉。附件来源是客户 / 现场 / 邮件，正好是不可信输入。

**修复**：

```go
var inlineOK = map[string]string{
	".png": "image/png", ".jpg": "image/jpeg", ".jpeg": "image/jpeg",
	".gif": "image/gif", ".webp": "image/webp", ".bmp": "image/bmp",
	".pdf": "application/pdf", ".txt": "text/plain; charset=utf-8",
}

func serveInline(w http.ResponseWriter, r *http.Request, p string) {
	ext := strings.ToLower(filepath.Ext(p))
	if ct, ok := inlineOK[ext]; ok {
		w.Header().Set("Content-Type", ct)
		w.Header().Set("Content-Disposition", "inline")
		w.Header().Set("Content-Security-Policy", "sandbox; default-src 'none'")
	} else {
		w.Header().Set("Content-Disposition", "attachment")
	}
	http.ServeFile(w, r, p)
}
```

> 注意 `Content-Type` 必须显式设置，否则 `ServeFile` 仍会按扩展名覆盖。SVG 千万不要放进白名单（SVG 内可嵌 `<script>`）。

### S2（中高危）内联 `onclick` 里拼 JS 字符串：HTML 转义救不了 JS 上下文

**位置**：`web/js/pages/projects.js:554`

```js
<button class="btn link" onclick="PG_PROJ.uploadVersion(${a.id},'${UI.esc(a.atype)}')">上传新版本</button>
```

这是全项目唯一一处把**非数字数据**塞进内联事件处理器的地方。`UI.esc` 会把 `'` 转成 `&#39;`，但 HTML 解析器在把属性值交给 JS 引擎**之前**会先把实体解码回 `'`，于是引号成功闭合：

```
atype = x'),alert(document.domain),('
属性 → onclick="PG_PROJ.uploadVersion(5,'x&#39;),alert(document.domain),(&#39;')"
JS   → PG_PROJ.uploadVersion(5,'x'),alert(document.domain),('')   ← 代码执行
```

`atype` 在 `handlers_projects.go:736` 只做了 `strings.TrimSpace`，没有白名单校验，任何能调 API 的客户端都可以写任意值；之后只要有人打开该项目的附件页就会触发（存储型）。在「单用户 + 局域网」的现实场景里，利用前提是攻击者已能发请求（或配合 S7 的 CSRF），所以定级为中高危而不是直接高危 —— 但这是一个**模式性错误**，代码里还有 78 处内联 `onclick`，下一次只要有人再拼一个字符串参数就会重演。

**修复**（同时是去掉内联事件的第一步）：

```js
// 数据放 data-*，事件交给委托
<button class="btn link" data-act="upload-version" data-id="${a.id}" data-atype="${UI.esc(a.atype)}">上传新版本</button>

// 渲染完成后统一绑定
view.addEventListener('click', e => {
  const btn = e.target.closest('[data-act]');
  if (!btn) return;
  if (btn.dataset.act === 'upload-version') PG_PROJ.uploadVersion(Number(btn.dataset.id), btn.dataset.atype);
});
```

> 通用规则：`innerHTML` 里只有两种安全插入方式 —— **纯文本节点**用 `UI.esc`，**属性值**用 `UI.esc`；一旦目标是「JS 代码字符串」，就必须用 `JSON.stringify` 或干脆不要内联。

### S3（中）未知 `/api/*` 路径返回 200 + `index.html`

**位置**：`internal/httpapi/server.go:251`（SPA 兜底 `m.HandleFunc("/", s.hStatic)`）+ `server.go:265-277`

**实测**：`GET /api/projectz`（拼错的接口）→ `200 OK, Content-Type: text/html`。前端 `api.js:22` 只在 `Content-Type` 含 `application/json` 时解析，于是拿到 HTML 后走到 `!res.ok` 分支之外，最终以 `Unexpected token '<'` 结束，提示信息完全误导；外部扫描器看到 200 也会误判接口存在。

**修复**：`hStatic` 开头加一行

```go
if strings.HasPrefix(r.URL.Path, "/api/") {
	writeErr(w, 404, "接口不存在")
	return
}
```

### S4（中）首次初始化没有本机限制

**位置**：`internal/httpapi/handlers_auth.go:27-31`；默认监听 `0.0.0.0` 见 `main.go:30`

`hSetup` 只判断「还没有用户」，不判断来源。程序默认对局域网开放，谁先打开页面谁就能设置管理员密码并接管全部数据。同一文件里的 `hResetToken` 已经做了 `isLoopbackReq` 校验（`:133`），说明作者知道这个风险，只是 setup 漏了。

**修复**：setup 也要求本机（或加 `-allow-remote-setup` 开关），README 里补一句「首次初始化请在服务器本机完成」。

### S5（低）缺少通用安全响应头

**实测**：首页与接口响应只有 `X-Content-Type-Options: nosniff`，没有 `Content-Security-Policy`、`X-Frame-Options` / `frame-ancestors`、`Referrer-Policy`。

内网自用风险有限，但加上成本极低，还能顺手压住 S1 的影响面：

```go
w.Header().Set("Content-Security-Policy", "default-src 'self'; img-src 'self' data: blob:; style-src 'self' 'unsafe-inline'; script-src 'self' 'unsafe-inline'")
w.Header().Set("X-Frame-Options", "DENY")
w.Header().Set("Referrer-Policy", "no-referrer")
```

> `script-src 'self' 'unsafe-inline'` 是因为 `index.html:22` 有内联 `App.boot()`、多处 `onclick="..."` 内联事件；要拿到严格 CSP 得先把内联事件改成 `addEventListener`（见 Q6）。

### S6（低）`hBlob` 用「删除 `..`」防穿越，方式脆弱

**位置**：`internal/httpapi/handlers_customers.go:482-491`

```go
sub = strings.ReplaceAll(sub, "..", "")
p := filepath.Join(s.st.Files, filepath.FromSlash(sub))
```

实测 `..%2f..%2f..%2fWindows%2fwin.ini` 返回 404、`....//....//Windows/win.ini` 返回 307，**当前不可利用**（`filepath.Join` 会 Clean，且 `http.ServeFile` 自身也会拦 `..`）。但这种「先替换再拼接」的写法以后很容易被改坏，建议直接换成可证明正确的形式：

```go
clean := filepath.Clean("/" + filepath.FromSlash(sub))     // 强制绝对化再 Clean
p := filepath.Join(s.st.Files, clean)
if !strings.HasPrefix(p, filepath.Clean(s.st.Files)+string(os.PathSeparator)) {
	writeErr(w, 403, "非法路径"); return
}
```

### S7（低，取决于使用场景）CSRF：同站不同端口可以绕过 SameSite

`web/js/api.js` 没有任何 CSRF token，`server.go` 也只检查会话 Cookie。`SameSite=Lax` 只挡「跨站」，而 `127.0.0.1:8787` 与 `127.0.0.1:9999`（本机其他随便什么服务）属于**同站**，Cookie 照样会带上；`application/json` 请求会触发预检被 CORS 挡住，但 **multipart 上传是 simple request**，不会预检 —— 也就是说别的本地页面可以静默往 `/api/projects/1/attachments` 塞文件（配合 S2 的 `atype` 还能落一个 XSS）。

局域网单用户场景下风险不高，但修复很便宜，二选一：

```go
// 后端：要求自定义头（简单请求带不上，天然需要预检）
if r.Method != http.MethodGet && r.Header.Get("X-Requested-With") != "XMLHttpRequest" {
	writeErr(w, 403, "非法请求"); return
}
// 前端 api.js 里所有 fetch 统一加：headers: { 'X-Requested-With': 'XMLHttpRequest' }
```

或者校验 `Origin` / `Sec-Fetch-Site`（只允许同源或 `same-origin`）。

## 三、正确性 Bug

### B1（中）维保到期当天的状态判断错误

**位置**：`internal/httpapi/handlers_projects.go:868`

```go
days := int(time.Until(ed).Hours() / 24)   // 负数向 0 截断
if days < 0 { st = "过保" } else if days <= warn { st = "即将过保" }
```

`int()` 对负数是向零截断：到期日是今天 00:00、现在是 21:00 时，`hours/24 = -0.87`，`int(-0.87) = 0`，于是判定为「在保 / 即将过保」，而实际已经过保近一天。SQL 侧同样的问题：`CAST(julianday(expire_date) - julianday(date('now','localtime')) AS INTEGER)`（`handlers_dashboard.go:119,127,147,255,277`、`handlers_export.go:337,665`）也向零截断。

**实测**：把某维保项目到期日设为今天 →

```
status = "即将过保"      （预期：过保）
days_left = 0            （预期：已过期）
```

用户在到期当天看到的是「剩 0 天」，而不是「已过保」，提醒文案也会说「剩余 0 天」。

**修复**：

```go
// Go 侧
if time.Now().After(ed) {
	st = "过保"
} else if time.Until(ed).Hours() <= float64(warn)*24 {
	st = "即将过保"
} else {
	st = "在保"
}

// SQL 侧
CAST(floor(julianday(m.expire_date) - julianday(date('now','localtime'))) AS INTEGER)
```

### B2（中）保存项目时重复写入关联关系

**位置**：`internal/httpapi/handlers_projects.go:275-287`（`applyProjectExtras` 里 `related_project_id` 分支，`create=false` 时也会执行）

**实测**：新建一个「加点」项目（关联项目 1），再连续保存 3 次编辑 →

```
project_relations 行数 = 4
id=1 related=1 addon_source
id=2 related=1 addon_source
id=3 related=1 addon_source
id=4 related=1 addon_source
```

「关联与转化」页会把同一个项目重复列 4 次。相关的小问题：编辑表单的「关联原项目」下拉没有回填既有关系（`projects.js:176` 读 `p.related_project_id`，但 `hProjectGet` 没有返回这个字段），所以用户重新选一次就又插一条。

**修复**（三选一，建议前两条一起做）：

1. `hProjectGet` 返回 `related_project_id`，编辑表单正确回填；
2. 只在 `create == true` 时写关系，更新走现有的 `hProjectRelationAdd`；
3. 字段加约束：`UNIQUE(project_id, related_project_id, rel_type)`，写之前 `ON CONFLICT DO NOTHING`。

### B3（中）多步写操作没有事务

**位置**：
- `handlers_projects.go:226-231`：建项目 → 产品 → 阶段模板 → 网络引用 → 维保信息
- `handlers_records.go:400-480`：项目转化（项目 / 阶段 / 产品 / 关联 / 网络 / 设备 / 附件 / 进度 / 维保）
- `handlers_customers.go:264-293`：先 `UPDATE net_versions SET is_current=0`，再插新版本、写差异

任何一步失败（磁盘满、约束冲突、进程被杀）都会留下半成品：项目没阶段、客户没有 `is_current` 版本、转化出了项目却没继承附件。`store` 里没有暴露事务接口，这些循环都直接 `Exec`。

**修复**：`store` 加一层

```go
func (s *Store) Tx(fn func(tx *sql.Tx) error) error {
	tx, err := s.DB.Begin()
	if err != nil { return err }
	if err := fn(tx); err != nil { tx.Rollback(); return err }
	return tx.Commit()
}
```

SQLite 单连接下事务没有额外开销，主要成本是把 handler 里的 `s.st.Exec` 改成 `tx.Exec`。

### B4（低）`projects.updated_at` 更新不一致

新建进度会 `UPDATE projects SET updated_at`（`handlers_records.go:82`），附件上传也会（`handlers_projects.go:788`）；但**新建 / 关闭问题**（`handlers_records.go:228-281`）、**更新维保**（`handlers_projects.go:899-948`）、**拓扑图上传**（`handlers_customers.go:445-480`）都不更新。项目列表按 `updated_at DESC` 排序（`handlers_projects.go:100`），于是「刚改过问题的项目」仍排在后面。

**修复**：抽一个 `touchProject(id)`，所有子资源写操作后统一调用；或干脆用触发器。

### B5（低）状态字典有三份，互相不一致

| 来源 | 内容 | 使用处 |

| `handlers_projects.go:25-48` `statusByType` / `statusOptions` | 按项目类型区分，维保含 `在保/即将过保/过保` | 只用于 `hProjectGet` 返回的 `status_options` |

### B6（低）非法导出类型返回 200 空工作簿

**位置**：`handlers_export.go:28-118`；`nameMap[typ]` 未命中时为空串，且没有任何 sheet 被添加。

### B7（低）备份并发共用一个临时文件名

**位置**：`handlers_backup.go:108`

```go
tmpDB := filepath.Join(s.st.Backups, ".snapshot.db")
_ = os.Remove(tmpDB)
if _, err := s.st.DB.Exec(`VACUUM INTO ?`, tmpDB); err != nil { ... }
```

手动「立即备份」和后台每分钟调度（`:222-250`）可能同时进入 `runBackup`，两者用同一个 `.snapshot.db`：一个 `Remove` 另一个正在读，或两个 `VACUUM INTO` 抢同一路径。另外 `pruneBackups`（`:175-194`）可能在 zip 还在写的时候删文件。

### B8（低）提醒扫描计数虚高

**位置**：`handlers_dashboard.go:271,288,300,313`，每处 `created++` 在 `addReminder` 之后无条件执行，而 `addReminder` 内部是 `ON CONFLICT(dedupe_key) DO NOTHING`。重复扫描时前端会显示「处理 N 条提醒条件」，但实际一条都没新增。

**修复**：让 `addReminder` 返回 `sql.Result.RowsAffected()`，只在真的插入时累加。

`UI.fmtDate` 对空值返回 `'—'`（`ui.js:17`），是 truthy，所以「无记录」这个分支永远走不到。

## 四、性能

> 先给结论：**当前数据量下没有明显卡顿**。实测 42 个项目 / 340 条进度时 `/api/progress` 34ms、`/api/dashboard` 9ms、`/api/projects` 5.6ms。问题在于实现是「每条记录一次查询」，数据量线性增长时耗时会跟着线性涨（乘上 N+1 的系数），属于「现在改很便宜、以后改很贵」的类型。

### P1（重点）`hydrateProgress` 是最典型的 N+1

**位置**：`internal/httpapi/handlers_records.go:31-52` —— 每条进度记录执行 2 次查询（阶段 + 附件）。

调用面很广：`/api/progress`（上限 500 条 → 1000 次查询）、首页看板的本周记录、项目详情、Excel 导出（`handlers_export.go:224`）、PDF 周报（`handlers_export.go:573`）。

**实测**：340 条进度 → `/api/progress` 34ms；同样的数据若只做 3 条查询应在 5ms 以内。

**修复**：一次查出所有关联行，用 map 归并

```go
func (s *Server) hydrateProgress(rows []map[string]any) {
	if len(rows) == 0 { return }
	ids := make([]any, 0, len(rows))
	ph := make([]string, 0, len(rows))
	for _, m := range rows {
		ids = append(ids, store.PickInt(m, "id")); ph = append(ph, "?")
	}
	in := strings.Join(ph, ",")

	stageMap := map[int64][]map[string]any{}
	if ss, _ := s.st.QueryMaps(`SELECT ps.progress_id, ps.stage_id, s.name, s.seq
		FROM progress_stages ps LEFT JOIN project_stages s ON s.id=ps.stage_id
		WHERE ps.progress_id IN (`+in+`) ORDER BY s.seq`, ids...); ss != nil {
		for _, st := range ss {
			pid := int64(store.PickInt(st, "progress_id"))
			stageMap[pid] = append(stageMap[pid], st)
		}
	}
	// attachments 同理
	for _, m := range rows { /* 从 map 取值填 stages / stage_names / attachments */ }
}
```

同类 N+1 一并处理：

| 位置 | 问题 |
|---|---|

### P2 `GetSetting` 每次都查库

**位置**：`internal/store/db.go:185-194`。被 `settingInt`（看板每次 4 次）、`refreshMaintStatus`（每个维保项目 1 次）、`hMeta`、`hGetSettings` 反复调用。settings 只有十来个键，完全不需要每次落库。

**修复**：`Store` 里加 `settings map[string]string` + `sync.RWMutex`，`Open()` 时一次性加载，`SetSetting` 写库后更新缓存。

### P3 只读查询也被串行化

**位置**：`db.go:57` `db.SetMaxOpenConns(1)`。WAL 模式下读可以与写并发，这里把读也排进同一队，P1 的 N+1 因此被进一步放大（每次查询都要等队）。

**建议**：保持写连接 1 个，另开一个只读连接池（`?mode=ro`）给 `QueryMaps` 用；或者简单点，把 `busy_timeout` 保留、`SetMaxOpenConns(4)`，配合 `synchronous=NORMAL`。

### P4 索引基本只覆盖了外键

现有索引只到 `(project_id)` 级别，几个高频查询用不上：

```sql
CREATE INDEX IF NOT EXISTS idx_prog_proj_date ON progress(project_id, record_date DESC);
CREATE INDEX IF NOT EXISTS idx_issue_proj_status ON issues(project_id, status);
CREATE INDEX IF NOT EXISTS idx_maint_expire ON maintenance(expire_date);
CREATE INDEX IF NOT EXISTS idx_reminder_state ON reminders(is_read, is_done, remind_at DESC);
CREATE INDEX IF NOT EXISTS idx_proj_updated ON projects(updated_at DESC);
CREATE INDEX IF NOT EXISTS idx_att_proj_type ON attachments(project_id, atype);
```

### P5 PDF 每次导出重新解析 9.7MB 字体

**位置**：`handlers_export.go:371-389`（`findCJKFont`）、`:495-504`（每次请求 `AddTTFFont`）。

**实测**：`/api/export/pdf?type=weekly` 首次 65ms、二次 37ms，其中很大一部分是 `simhei.ttf`（9,745,792 字节）的解析。导出频率不高，但这是「一次缓存终身受益」的改动。

**修复**：`sync.Once` + `[]byte` 缓存字体字节，或按字体路径缓存 `*gopdf.GoPdf` 模板。

### P6 前端：重复拉全量列表

`records.js:158-161`（进度页）、`records.js:207-210`（问题页）、`projects.js:13-17`（项目表单）每次都额外请求 `/api/customers` + `/api/projects` 全量，只为填一个下拉框。项目上百个时，每开一次页面就多传几十 KB。

**建议**：`App.state` 里缓存 `customers` / `projects` 列表（写操作后失效），或提供 `/api/lookup` 只返回 `id + name`。

### P7 静态资源没有协商缓存，也没有压缩

**位置**：`server.go:265-277`

**实测**：`GET /js/app.js` 响应只有 `Content-Length` / `Content-Type`，**没有 `ETag`、没有 `Last-Modified`、没有 `Cache-Control`**（`embed` 文件时间是零值）。每次刷新页面都要重新下 64KB JS + 18KB CSS，且没有 gzip。

**修复**：

```go
// 1) 给静态资源加缓存头（index.html 必须 no-cache，否则升级后拿不到新版本）
if strings.HasSuffix(name, ".html") {
	w.Header().Set("Cache-Control", "no-cache")
} else {
	w.Header().Set("Cache-Control", "public, max-age=86400")
}
// 2) index.html 里给脚本加版本号：<script src="/js/app.js?v=1.0.0">
```

## 五、可维护性与工程化

### C1 没有任何测试

`0` 个 `_test.go`。纯函数其实很好测，建议先补最容易出错的几个：`parseDate` / `staleDays` / `weekRange` / `statusOptions` / `nextBackupTime` / `pbkdf2` 与 `Verify` 往返 / `truncateRunes`。`store` 用 `PM_DATA_DIR` 指向临时目录即可建库测试（环境变量已经在 `db.go:25` 支持），这是这个项目最容易补测试的地方。

### C2 gofmt 不干净 + 缺 `.gitattributes`

- LF 归一化后 `gofmt -l` 仍报 5 个文件：`handlers_dashboard.go`、`handlers_projects.go`、`handlers_records.go`、`server.go`、`db.go`（单行函数被拆行、`Now/Today` 对齐等）。

```bash
gofmt -w .          # 先修 5 个文件
printf '* text=auto\n*.go text eol=lf\n*.js text eol=lf\n*.css text eol=lf\n*.sh text eol=lf\n*.bat text eol=crlf\n' > .gitattributes
```

### C3 死代码与占位符

`var _ = sql.ErrNoRows`（`handlers_backup.go:252`、`handlers_customers.go:537`）、`var _ = json.Marshal`（`handlers_export.go:705`）、`var _ = io.EOF`（`handlers_projects.go:979`）—— 都是为了压掉未使用 import 的补丁；`_ = att`（`handlers_projects.go:761`）是查了不用的变量；`applyProjectExtras(r *http.Request, ...)`（`handlers_projects.go:236`）的 `r` 从未使用。建议删掉并清理对应 import，让「读代码时不用猜」这件事变简单。

### C4 重复样板

- 6 个 `sheetXxx()` 函数结构完全一样（`handlers_export.go:172-358`），可以抽 `buildSheet(st, sqlStr, args, cols, mapper)`。
- 每个 handler 都是「`reqID` → `readJSON` → `Update(table, fields)` → `ok`」，约 40 处同构代码；错误处理（`writeErr(w, 500, err.Error())`）也重复了 100+ 次。
- 前端 `innerHTML = 表格 + 分页 + 筛选` 的模式在 5 个页面里重复，`UI.table()` 已经有了，但 `projects.js` / `records.js` 仍手写 `<tr><td>`（因为需要自定义列 + 按钮）。
- `sheetProjects(st, r)` 里 `s := &Server{st: st}`（`handlers_export.go:173`）伪造 Server 对象来调 `hydrateProgress`，这是明显的分层味道：这些函数应该是 `*Server` 的方法。

### C5 版本号三处硬编码

`main.go:26` `const version = "1.0.0"`、`handlers_auth.go:23` `"version": "1.0.0"`、`app.js:155` `v1.0.0 · 本地版`。改一次要动三处，且没有 `-ldflags -X` 注入。建议 `main` 把版本传给 `httpapi.New`，前端从 `/api/state` 读。

### C6 没有优雅关闭，也没有日志

`main.go:90-100` 的 `os.Exit(0)` 直接退出：`http.Serve` 没走 `Shutdown`（正在上传的附件会被截断）、`db.Close()` 没调用（WAL 不 checkpoint，虽然后续启动能恢复）、后台备份协程被杀在半路。

同时整个服务**没有一行访问日志**（只有启动横幅）。出问题只能靠猜。建议：

```go
srv := &http.Server{Handler: loggingMiddleware(h), ReadHeaderTimeout: 10 * time.Second}
go func() { <-sigCh; ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second); defer cancel(); srv.Shutdown(ctx); st.DB.Close() }()
```

日志建议写到数据目录 `logs/app.log` 并轮转，字段含 method / path / status / 耗时 / 来源 IP。

### C7 没有 CI

建议加一个最小的 `.github/workflows/ci.yml`：`gofmt -l`、`go vet ./...`、`go test ./...`、`GOOS=linux/windows go build`。这个项目跨平台编译是卖点，但完全靠手工验证。

### C8 schema 没有迁移机制

`schema.go` 全是 `CREATE TABLE IF NOT EXISTS`，后续加字段只能靠用户手改库。建议引入 `PRAGMA user_version` + 顺序迁移列表，`Open()` 时检查并逐条升级（对已有数据目录是硬需求，因为 README 说「迁移 = 拷目录」，用户库里是有真实数据的）。

### C9 表缺外键 → 孤儿行

`net_changes.version_id`、`device_changes.device_id`、`project_device_changes.snapshot_id`、`progress_stages.stage_id`、`project_relations.related_project_id` 都没有 `REFERENCES`。删客户 / 删设备 / 删项目后，这些变更历史会永久留在库里；`hCustomerDelete`（`handlers_customers.go:100-116`）也不会清理 `topology` 引用的 `files/misc/*` 文件，磁盘会慢慢涨。

建议：新表补 `ON DELETE CASCADE`，启动时跑一次一次性清理（孤儿行 + 无引用文件），并在「系统 / 备份」页显示数据目录占用。

### C10 README 与实现的小出入

- `build.bat` 报错文案写「请先安装 Go 1.21+」，而 `go.mod` 要求 `go 1.26.0`。
- README「已知限制」没提「无测试」「备份无恢复」「S3 未接入」（后者提到了，前两者没提）。
- 直接双击 `项目管理.exe`（不经 `.bat` 的 `chcp 65001`）时，中文控制台输出在 GBK 代码页可能乱码 —— 建议启动时调用 `SetConsoleOutputCP(65001)`（`golang.org/x/sys/windows`），或者 README 统一引导用 `启动.bat`。

## 六、前端专项

### F1（中）路由切换没有请求取消，旧页面会覆盖新页面

`app.js:292-325` 的 `route()` 先写入「加载中…」，随后各页面异步 `await` 完成后直接 `view.innerHTML = ...`。快速点两个菜单时，先发的请求（更慢的那个）后返回，会把当前页面覆盖成上一个页面。

**修复**：给 `App` 加一个自增 `navToken`，页面函数拿到时比对；或用 `AbortController` 随路由 abort（`api.js:3` 的 `req` 加 `signal` 参数）。

### F2（低）重复绑定 document 级监听

`app.js:254` 的 `bindSearch()` 在每次 `renderShell()` 时都 `document.addEventListener('click', ...)`，登录 → 退出 → 再登录会累积多个监听器。`ui.js:61` 的 `keydown` 监听有 `removeEventListener`（正确），可以作为对照。

### F3（低）`UI.pageHead` 的标题是 `innerHTML` 直出

`ui.js:229` `pageHead(title,...)` 把 `title` 原样插入 HTML，调用方必须自己 `UI.esc`。目前所有调用点都传静态串或已转义（`projects.js:224` 等），但这是个「下一个人一定会踩」的接口设计。建议标题走 `this.esc()`，需要富文本的另开 `pageHeadHTML`。

### F4（低）空 hook 与未使用参数

`records.js:112` `_afterIssues(pid) { }`；`records.js:4`、`records.js:88` 的 `withActions` 参数从未使用；`progressTable(pid, _rows, ...)` 的 `_rows` 也没用（函数内部重新请求了一次，等于调用方白查一遍）。项目详情页因此会重复请求 `/api/projects/{id}/progress`。

### F5（低）列表页全量渲染，没有分页 / 虚拟滚动

`projects.js:23-38`、`records.js:162-172` 一次性拼 500 行 HTML 字符串。500 行还能接受，上千行会明显卡（每次操作都是整表 `innerHTML` 替换）。更麻烦的是后端 `handlers_records.go:185` 的 `LIMIT 500`、`handlers_dashboard.go:196` 的 `LIMIT 300` 是**静默截断**，而前端写的是「共 N 条」（`records.js:173`、`records.js:226`）—— N 是截断后的数，用户会以为数据丢了。

**建议**：列表接口加 `page` / `page_size` 并返回 `total`，前端显示「共 N 条，当前第 x/y 页」。

### F6（中）接口失败后页面永远停在「加载中…」

`app.js:300`

```js
const run = fn => { try { fn(); } catch (e) { ... } };
```

`fn()` 返回的是 Promise，`try/catch` 抓不到异步抛错。各页面函数内部又没有 `try/catch`（`home.js:6` 是 `catch (e) { return; }`），所以只要 `/api/dashboard` 返回 500 / 超时，视图就永久停在 `<div class="empty-state">加载中…</div>`，用户既看不到错误也无法重试。

**修复**：把 `run` 改成 `const run = async fn => { try { await fn(); } catch (e) { ...错误卡片 + 重试按钮... } }`，并让 `API.req` 的错误信息透出（`api.js:25` 已经在 toast 里显示了，加上视图内提示即可）。

### F7（低）手写的「保存」按钮没有防重复提交

`UI.form` 里有 `btn.disabled = true`（`ui.js:168-169`），但手写的表单没有：`projects.js:190`（项目保存）、`projects.js:772`（转化表单）、`misc.js:221`（保存设置）。后端 `POST /api/projects` 不去重，双击「保存」就是两条一模一样的新项目。

**修复**：统一走 `UI.form`，或在 `onclick` 开头 `this.disabled = true`。

### F8（低）`UI.confirm` 按 Esc / 点遮罩后 Promise 永不 resolve

`ui.js:68-81` 只处理了「确定」「取消」两个按钮的 `onclick`，而 `modal()` 的 `close()` 会在 Esc 和遮罩点击时触发（`ui.js:59-64`），此时 `onClose` 是 `undefined`，Promise 悬空。调用方 `await UI.confirm(...)` 之后的代码永远不执行 —— 表现是「按 Esc 后按钮像坏了」。

**修复**：`UI.confirm` 传入 `onClose: () => { if (!done) resolve(false); }`。

### F9（低）文件选择框成功后不清空，同一个文件无法重试

`customers.js:332`、`projects.js:467` 的 `<input type="file">` 在 `onchange` 里上传后不移除文件，用户想重传同一个文件（例如第一次因网络失败）时 `change` 事件不触发。

**修复**：`e.target.value = ''`（或 `e.target.files = null` 不生效，用 `value=''`）。

### F10（低）`.card { overflow: hidden }` 让宽表在窄屏被裁掉且无法滚动

`app.css:135` 给卡片加了 `overflow: hidden`（大概率是为了圆角裁剪），`app.css:167-175` 的 `table.tbl` 是 `width:100%` + 单元格 `nowrap`。项目列表有 12 列，在 1280px 以下（或侧栏展开 + 分屏）会横向溢出，而卡片把溢出裁掉 —— 用户看不到右侧列，也不能横向滚动。整个 CSS 只有一个 `@media (max-width:1180px)` 且只调了看板栅格（`app.css:284`）。

**建议**：给表格套一层 `<div style="overflow-x:auto">`，或把 `.card` 改成 `overflow: visible` + `.body.tight{overflow-x:auto}`；顺带补两个断点（≤1024 侧栏折叠、≤720 表单单列）。

### F11 值得保留的好实践

`UI.esc` 在所有动态文本处基本都用对了（只有上面 F3 这种接口层面的风险）；`api.js:17` 统一处理 401 并跳登录；`UI.modal` 正确清理 `keydown` 监听；`UI.form` 统一了必填校验和提交态；`UI.table` 的 `render` 回调让列表结构化。这些别改。

### 补丁 1 —— `server.go` hStatic：`/api` 404 + 静态缓存头

```go
func (s *Server) hStatic(w http.ResponseWriter, r *http.Request) {
	if strings.HasPrefix(r.URL.Path, "/api/") {
		writeErr(w, 404, "接口不存在")
		return
	}
	name := strings.TrimPrefix(r.URL.Path, "/")
	if name == "" {
		name = "index.html"
	}
	if strings.HasSuffix(name, ".html") || name == "index.html" {
		w.Header().Set("Cache-Control", "no-cache")
	} else {
		w.Header().Set("Cache-Control", "public, max-age=86400")
	}
	if f, err := s.web.Open(name); err == nil {
		f.Close()
		http.ServeFileFS(w, r, s.web, name)
		return
	}
	http.ServeFileFS(w, r, s.web, "index.html")
}
```

### 补丁 2 —— `refreshMaintStatus`：不再截断负数天数

```go
func (s *Server) refreshMaintStatus(projectID int64) {
	m, err := s.st.QueryRowMap(`SELECT * FROM maintenance WHERE project_id=?`, projectID)
	if err != nil || store.PickInt(m, "manual_override") == 1 {
		return
	}
	ed, err := parseDate(store.Pick(m, "expire_date"))
	if err != nil {
		return
	}
	warn := s.settingInt("warranty_notice", 60)

	}
```

### 补丁 3 —— `store`：设置缓存 + 事务入口

```go
type Store struct {
	DB      *sql.DB
	DataDir string
	Files   string
	Backups string

	setMu sync.RWMutex
	sets  map[string]string
}

func (s *Store) GetSetting(key string) string {
	s.setMu.RLock()
	v := s.sets[key]
	s.setMu.RUnlock()
	return v
}

func (s *Store) SetSetting(key, value string) error {
	if _, err := s.DB.Exec(`INSERT INTO settings(key,value) VALUES(?,?)
		ON CONFLICT(key) DO UPDATE SET value=excluded.value`, key, value); err != nil {
		return err
	}
	s.setMu.Lock()
	s.sets[key] = value
	s.setMu.Unlock()
	return nil
}

func (s *Store) Tx(fn func(tx *sql.Tx) error) error {
	tx, err := s.DB.Begin()
	if err != nil { return err }
	if err := fn(tx); err != nil { _ = tx.Rollback(); return err }
	return tx.Commit()
}
```

> `Open()` 里建表后先 `SELECT key,value FROM settings` 灌满 `s.sets`，即可。
